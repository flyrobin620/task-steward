1. 背景与目标

用户 2026-11-09 提出（T246）：

研究怎么把它放在task-steward的plugin marketplace里面，可以通过repo distribute给其他人，task-steward应当有能力distribute 一些东西，包括他自己的plugin，还有code agent的plugin（skill+mcp）等

这也是 release.md 中尚未决定的“插件分发方式”。本文回答：

  1. TaskSteward 自己的插件怎样经仓库发布、安装、更新；
  2. 用户在工作中积累的 code agent 插件（skill，或 skill 加 MCP server）怎样经仓库分发给自己的其他会话、其他机器和别人，TaskSteward 在其中做什么；
  3. 版本、更新与来源可信的做法；数据目录里的 skill 与插件里的 skill 是什么关系。

本文写与宿主无关的设计；Claude Code 与 Codex 的具体做法见 CC009 与 CX009。

2. 要分发的三类东西

类别例子内容公开性
TaskSteward 自己的插件task-stewardtsw MCP server、hooks；运行时是 tsw 包公开
通用的 code agent 插件只含 skill 的插件；skill 加 MCP server 的插件skill、MCP 声明、可选 hooks视内容而定
个人或团队的工作流插件周报、团队消息之类的 skill常含身份、名单、内部项目名私有

3. 原则

  1. 不自造格式。 分发单位是 Claude Code 格式的插件目录（skills/、.mcp.json、可选 hooks/ 与 .claude-plugin/plugin.json），目录由仓库中的 .claude-plugin/marketplace.json 列出。Codex 也读取这份清单并安装这种格式的插件（CX009），所以一份内容服务两个宿主，宿主之间只差“登记与启用”这一步。
  2. 按可见性分市场。 一个市场的全部条目对添加它的每个人可见，市场没有按人过滤的字段，所以公开仓库的市场只放公开内容，个人或团队内容放私有市场仓库。
  3. 来源在 git 仓库，不在数据目录。 数据目录里的 skill 只是草稿：没有版本，不在 tsw backup 的范围（DN006 §9.5），也到不了数据目录之外的会话。要长期保留或分享的插件放进市场仓库，经 PR 修改。
  4. tsw 不改用户或全局配置。 延续 DN006 §6.2 的 install_hint：用户级的安装与启用由 tsw 给出命令，用户执行。
  5. 插件可信，检查只防错（DN008）。 tsw 不审查插件做什么。确定性检查只防已知的错：把私有内容放进公开市场、改了插件却没改版本导致别人拿不到更新、清单写错。这些检查放在打包与 PR 门禁中，不新增 hooks 护栏规则。宿主自己的确认（项目插件的 MCP 批准、Codex 的 hook 信任）照常进行，tsw 不绕过。

4. TaskSteward 自己的插件

4.1 市场与版本

  • 本仓库自带市场清单 .claude-plugin/marketplace.json，市场名 task-steward，只列一个条目 task-steward（来源 ./plugin）。
  • 发布后：版本只有一个来源 tsw.__version__，plugin/.claude-plugin/plugin.json 的 version 与它相同（测试检查二者一致），市场条目不写 version；从 main 上的提交打标签 vX.Y.Z（release.md）。
  • 开发期：plugin.json 不写固定的 version。宿主按版本字符串判断是否更新，固定的 0.1.0-dev 会让已安装的副本永远不更新：本机实测，app 运行的是插件缓存中 2026-11-06 的副本（MCP server 的命令行指向缓存目录），其中还有已经删除的 skills/orchestrate、旧的 hooks matcher 与旧的启动器，claude plugin update 也不会替换它（CC009 §2）。不写版本时，git 市场中的相对路径插件以提交 SHA 为版本，每次更新都能拿到新副本。现在的 plugin.json 仍写着 0.1.0-dev，由 §9 的 S1 改掉。
  • 启动器在会话开始时比较自己所在的插件目录与产品仓库中的 plugin/：内容不一致时，在会话上下文中提示一次“已安装的插件副本过期”和更新命令，不阻断（只防错，DN008）。

4.2 安装方式

插件运行时需要 tsw 包，而用户本来就需要产品仓库的检出来运行 tsw init、tsw host render 等命令（DN006 §9.7），所以：

方式做法运行时结论
A 检出标签 + 本地目录市场git clone 后检出 vX.Y.Z；以检出目录添加本地市场并安装插件启动器在插件所在仓库中找到 tsw，与插件同一版本推荐：一个检出同时提供 CLI 与插件，版本不会错开
B GitHub 市场添加 flyrobin620/task-steward#vX.Y.Z 并安装插件插件被复制进缓存，启动器按 tsw init 记录的 product_repo 找运行时可选：适合已有检出、只想按标签更新插件的用户；启动器比较 plugin.json 的版本与运行时的 __version__，不一致时 MCP server 报错，hooks 放行并提示
C 运行时随插件分发发布时把 tsw 包放进插件目录（构建产物或市场内符号链接）插件自带暂不做：只在不再需要检出时才有意义（例如发布到 PyPI）；符号链接在 Windows 上需要开发者模式，构建产物需要发布流水线

v1 不发布到 PyPI。

4.3 更新

用户按标签更新：方式 A 检出新标签后更新插件；方式 B 更新市场与插件。之后重新加载插件或重启会话，再运行 tsw host render（数据目录的 CLAUDE.md 与主会话 skill 随产品更新）。宿主的自动更新默认关闭，tsw 不替用户开启。

5. code agent 插件

5.1 插件的形态

  • 一个插件一个目录：skills/<名>/SKILL.md，需要 MCP server 时有 .mcp.json（命令与参数用插件根目录变量引用插件内的文件），需要时有 hooks/，plugin.json 写名称、说明与参数声明。
  • 个人数据参数化：身份、收件人、名单路径等写成插件的用户参数（Claude Code 的 userConfig，启用时提示填写，敏感值进系统凭据库），skill 正文引用参数，不写死。Codex 没有对应的文档化机制（CX009 §4），跨宿主的插件把参数放在插件说明的配置文件中，由 skill 读取。
  • 插件里的 skill 带命名空间（Claude Code 为 <插件>:<skill>），与数据目录中的同名 skill 不冲突，但会同时出现（§6）。

5.2 市场仓库

市场放什么谁能添加
本仓库的 task-steward 市场TaskSteward 自己的插件；将来经用户决定、内容可以公开的通用插件任何人
用户自己的私有市场仓库个人与团队的工作流插件；第三方插件的引用（按 sha 固定到其他仓库的提交或子目录）有仓库读权限、本机已存好 git 凭据的人
组织内已有的共享市场准备给组织内同事用、已参数化的插件组织成员

私有仓库的访问完全由宿主调用本机 git 时的凭据决定，市场清单中没有凭据字段（CC009 §5）。

5.3 打包与发布：一个普通的 TaskSteward 任务

“TaskSteward 有能力分发”的含义是：把一个 skill 或插件放进市场仓库，是在已登记的市场仓库上执行的普通任务，走 worktree、自评审、PR、CI 与合并（DN002）。主会话按用户的要求登记这类任务，例如“把数据目录里的周报 skill 打包进我的私有市场”。worker 的步骤：

  1. 把草稿从数据目录（或别处）复制进市场仓库的插件目录；
  2. 把个人数据改为用户参数；
  3. 写 plugin.json 与市场条目，按 §7 处理版本；
  4. 运行宿主的清单校验（Claude Code 为 claude plugin validate），以及市场仓库自己的门禁；
  5. 目标市场公开时，运行隐私扫描（复用本仓库的隐私规则与本机私有词表，docs.md）；
  6. 开 PR，自评审，合并后告诉用户安装或更新命令。

tsw 为此提供一个确定性检查 tsw dist check <市场根目录>（实现拆分 S3）：清单可解析、条目名合法且不重复、相对路径不越出市场根目录；插件内容相对上一次发布有变化而版本字符串没变时报错；市场标为公开时运行隐私扫描。市场仓库的 CI 可以直接调用它。

5.4 让 TaskSteward 的会话用上插件

TaskSteward 的会话分布在三类目录：数据目录（主会话）、数据目录下的 work/<任务>/<attempt> 与 routine/（研究类 worker 与例行会话）、数据目录之外的 worktree（设计与开发类 worker）。宿主按会话目录决定加载哪些项目设置与项目插件，而执行目录不能带自己的设置文件（带了会再次要求信任，决定记录 0003）。因此：

安装位置主会话work/、routine/ 中的会话worktree 中的 worker
用户范围的插件能用能用能用
数据目录项目范围的插件能用不能用不能用
数据目录 .claude/skills/ 中的普通 skill能用能用（宿主向上级目录查找 skill）不能用

宿主各自的依据见 CC009 §3 与 CX009 §3。结论：

  • 要给 worker 用的插件，装在用户范围。 这也是 TaskSteward 自己插件的做法（CC006 §2）。担心影响无关会话时，插件自己按会话目录判断是否生效，tsw 的 hooks 就是这样做的。
  • 只在主会话用、或还在试用的 skill，可以留在数据目录 .claude/skills/。
  • 用户范围的安装由用户执行 tsw 给出的命令（§3 第 4 条）。统一配置可以记录“TaskSteward 期望的插件”（实现拆分 S4），tsw host install-hint 与状态页据此列出缺少或过期的插件；例如 teams-chat 渠道需要的 Teams 工具。

6. 数据目录 skill 与插件 skill 的关系

  • tsw host render 只写自己拥有的文件：数据目录的 CLAUDE.md、orchestrate 与 handle-input 两个 skill、.claude/settings.json 中的允许规则。它不删除也不改写 .claude/skills/ 下的其他 skill，分发也不使用这两个名字，所以分发不影响主会话的流程说明。
  • 主会话的流程说明不进插件：用户范围的插件在任何目录都加载，而 orchestrate 只应在数据目录中出现（CC006 §2）。本机的过期插件副本中还留着旧的 skills/orchestrate，会以 task-steward:orchestrate 与数据目录的 orchestrate 同时出现；§4.1 的版本规则修好后它随更新消失。
  • 一个 skill 发布成插件并装好后，删掉数据目录中的草稿副本，避免同一件事有两个触发入口、两份内容各自漂移。
  • 数据目录中的用户 skill 不在 tsw backup 范围；要保留的放进市场仓库。

7. 版本、更新与来源可信

对象版本更新来源固定
TaskSteward 插件（发布后）plugin.json = tsw.__version__，标签 vX.Y.Z用户按标签更新标签
TaskSteward 插件（开发期）不写，按提交 SHA用户更新插件；启动器提示过期副本本地检出
私有市场中自己的插件不写，按提交 SHA；每次合并即发布用户更新市场与插件，或对这个市场开启自动更新市场仓库的分支
共享或公开市场中的插件写 version，每次发布递增同上版本字符串
第三方插件由对方决定改条目中的 sha 并经 PR条目写 sha

可信：按 DN008，用户安装的插件可信；它们的 hooks 与 MCP server 以用户权限运行。PR 正文列出新增或改动的 hooks 与 MCP 命令，便于用户在合并前看清会运行什么；这是评审信息，不是 tsw 的拦截。

8. 方案

方案内容优点缺点
甲（推荐）本仓库市场只发布 TaskSteward 自己（§4，安装方式 A）；个人与团队插件放用户的私有市场仓库，打包作为普通任务（§5.3）；给 worker 用的插件装在用户范围（§5.4）不造格式，两个宿主共用；公开与私有分开；分发走已有的任务、评审与合并流程用户要建并维护一个私有仓库；用户范围的插件在所有会话加载
乙所有插件都放本仓库的公开市场只有一个市场个人内容必须完全参数化并去掉内部信息，稍有遗漏就公开；每次改动都要走本仓库的门禁与用户确认
丙不做插件：可分发的 skill 放在一个 git 仓库的目录里，由 tsw host render 复制进数据目录 .claude/skills/最简单；主会话与 work/ 中的 worker 不需要安装不能带 MCP 或 hooks；worktree 中的 worker 与 Codex 用不到；别人要用还得装 TaskSteward
丁经组织内已有的共享市场分发同事一键安装受组织市场的规则约束；只适合已参数化、可在组织内公开的插件；可与甲并用
