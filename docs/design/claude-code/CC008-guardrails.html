1. 目标

按 DN008 在 Claude Code（桌面 app 与命令行）上实现护栏，尽可能薄：一般风险交给 Claude Code 自己的权限模式与 auto 分类器；tsw 只加宿主不知道的、确定性的 block list 规则。规则越少，规则本身出错的机会越少。

“现状”指 main（含 T241，#18）上的实现。

2. 分工

层判断什么是否 LLM在 Claude Code 中
Claude Code 权限模式与 auto 分类器一般风险：删除、写到意外的位置、危险命令；一次调用是否出自用户意图是（宿主的保护，不是 tsw 的护栏，DN008 §4 第 3 条）会话的权限模式；worker 建议使用 auto（roles.worker.permission_mode）
tsw 生成的允许规则与 auto 模式规则把“授权记录在 tsw 中、由 tsw 把关”的动作从分类器的判断中移出否主会话：数据目录生成的 permissions.allow；worker：执行目录不带规则，只靠用户加入用户设置的 autoMode.allow 规则（install hint 给出，§6）
tsw hooks 的 block listtsw 特有的已知错误（§3）否PreToolUse 调用 tsw guard
tsw MCP 与状态机角色、任务、租约、版本、G-*、用户来源（DN008 §6）否MCP server 按角色列出工具；run_tool 的检查与各工具的守卫
事后发现漏网的偏差（不保证发现）部分流程（确定性）：ledger audit 的摘要链、G-SUBMIT / G-ACCEPT 对提交、登记与处置记录的检查。内容（LLM）：主会话验收时判断 diff、PR 与合并后的 CI，不是护栏

权限模式为 bypassPermissions 时没有分类器，一般风险没有宿主保护；这是用户自己的选择，tsw 不补上。

3. block list

所有规则只在已登记的会话（主会话、worker、例行会话、已撤销、待绑定）中生效，无关会话不受影响。规则只看工具名、目标路径前缀、命令中的程序与子命令（分词，不解析路径、重定向、变量与脚本）。

编号会话触发防的错误拒绝信息中的正确做法
CC-B1所有编辑类工具（Edit / Write / MultiEdit / NotebookEdit）的目标在数据目录的 ledger/ runs/ todo/ config/ outbox/ legacy/ views/ cache/ locks/ 中手工“修”账本、把报告直接写进 runs/、编辑配置文件（走错步骤）对应的 tsw 工具：报告写在 work/ 由 submit 导入；配置用 config_change
CC-B2所有编辑类工具的目标是数据目录（含其下执行目录）中的 .claude/settings*.json遇到权限拒绝后自行添加允许规则，越过用户选定的权限；改动被 tsw 重新生成覆盖把权限拒绝告诉用户，由用户决定
CC-B3worker编辑类工具的目标在本任务仓库的主检出（repositories.<repo>.path）中，而执行目录不在其中写进主仓库检出而不是任务 worktree（对象错误）在执行目录（任务 worktree）中修改
CC-B4workergit … push，仓库没有 delivery.push未授权的远端动作不推送；提交时说明
CC-B5workergh pr create，仓库没有 delivery.create_pr同上同上
CC-B6workergh pr merge，或 gh api 调用 REST 合并路径（…/pulls/<n>/merge）或 GraphQL mergePullRequest（只看这两种写法，不看评论正文等其他参数里的 “merge” 一词：现状对此误拦，本任务回复评审线程时实测）；仓库没有 delivery.merge（不看任务类型，T245）不该由 worker 合并时合并，主会话流程随之错乱提交时用 merge_skipped 说明，由主会话合并。不可放行：它是 G-SUBMIT 合并授权的镜像，放行后合并记录仍会被 G-SUBMIT 拒绝；需要 worker 合并时由用户修改 delivery.merge（用户在会话外手工编辑，或经主会话 config_change），然后在原 worker 中重试：hook 与 G-SUBMIT 每次都重新读取配置，不需要重启会话
CC-B7worker有合并授权，但 gh pr merge 没有 -R HOST/OWNER/NAME 或本仓库的 PR 链接与配置的 host（默认 github.com）、repository 一致；或用 gh api 合并按当前目录或遗留的 GH_HOST 合并了别的仓库或别的主机的 PR（目标错误）gh pr merge <编号> -R github.com/<owner>/<name>，或该仓库的 PR 链接
CC-B8worker、主会话、例行会话CronCreate / ScheduleWakeup 的提示不以 <scheduled-task> 开头定时提示到达时与用户消息无法区分：worker 的被记成用户答复（live host-e2e 实测，误认来源）；主会话的被当成用户本人的 turn，CC-S4 随之要求在不能创建会话的 turn 中预启动（T244）提示以 <scheduled-task> 开头、</scheduled-task> 结束
CC-B9主会话start_session 的会话名不是已落账、代次有效的 attempt，也不是正在启动的例行会话代次没有先 attempt_start / routine_start 就建会话，或重复建会话先 attempt_start（例行会话先 routine_start），用返回的会话名。不可放行：没有落账的会话无法绑定到 attempt（DN002 §6）
CC-B10已撤销 / 待绑定编辑类工具、Bash、start_session已被替换的会话继续写；绑定前就开始工作（状态漂移）已撤销：回到主会话；待绑定：等主会话绑定后的消息
CC-B11例行会话编辑类工具、Bash、start_session例行会话自己去“处理”问题（改代码、跑命令、建会话），越过“只执行例行动作、不作判断”的分工（DN006 §8.9）只执行例行表（routine_board）中的例行项；其余事项发消息交主会话

escape（DN008 §5 第 4 条）：每条拒绝信息以规则编号开头，写出上表的正确做法；可放行的规则还写明“动作确属任务需要时，问用户；用户同意后用 user_answer 登记放行这条规则”。CC-B6、CC-B9 是状态机守卫的镜像，不能放行或关闭（waive_rules 与 guardrails.disabled 中出现它们时以 invalid_input 拒绝），只给出状态机的路径。其余规则的做法：

  1. 就地放行（worker）：worker 用 ask_user 说明被拦下的动作与理由；用户在 worker 会话中回复后，worker 调用 user_answer，除答复外带上 waive_rules（如 ["CC-B4"]）。tsw 用 hook 记录的用户原话记录 guardrail.waived（规则编号、attempt、用户来源）。hook 对该 attempt 不再执行这些规则；attempt 结束即失效。这与评审预算追加的做法相同（DN006 §8.1a），不需要主会话参与。
  2. 长期关闭（用户）：配置 guardrails.disabled 列出的规则对所有会话不再拦截。它是新的权限类键（DN003 §7.2），由主会话按用户在主会话或其他渠道的原话修改；worker 会话中的原话只用于就地放行，不改全局配置。
  3. 主会话被拦下（CC-B1、CC-B2）：在主会话中问用户，按用户的话用 config_change 写入 guardrails.disabled，或由用户自己执行。CC-B9 不可关闭：先 attempt_start，再用返回的会话名创建会话。
  4. 用户自己做：用户总可以在会话外自己执行被拦下的动作。

CC-B8 的背景（自 DN006 §8.1b 移入）：定时提示到达会话的方式与用户消息相同，UserPromptSubmit 的 payload 中没有区分来源的字段（live host-e2e 中，worker 用 CronCreate 设的唤醒提示被记成了用户消息，转交因此以 user_responded 被拒）。因此 worker 调用宿主的定时工具（CronCreate、ScheduleWakeup）时，提示必须以 <scheduled-task> 开头，PreToolUse hook 拒绝其他写法；带这个标记的消息与其他注入消息一样不记录。主会话记下用户 turn（CC-S6）之后，同样的规则也用于主会话（T244）：不带标记的定时提示会被当成用户本人的 turn。

失败方式：hook 内部异常时放行并在 stderr 报告（现状不变）。

4. 其他 hooks

编号hook行为归类
CC-S1SessionStart识别角色；主会话领取租约并注入 attention 摘要（让出过租约的会话不领取，只注入只读说明，DN001 §6.4，T254）；worker 注入任务、任务书路径与可写路径，并指向任务书开头的 worker 说明（回传与唤醒规则在其中，T276）；待绑定会话提示等待绑定保留（不是拦截）
CC-S2UserPromptSubmit（worker）live worker 的任务不是 accepted / cancelled / archived 时（T262 前只在有待答问题时），把用户消息原文记为 input.session_message 并告诉 worker 编号，可用于登记答复（user_answer）或需求变更（requirement_change，DN002 §5.1a）；去掉宿主前置的 <system-reminder>（T241）；以 <cross-session-message <side-sessions-event <task-notification <ci-monitor-event <scheduled-task 开头的注入消息不记保留。前置 reminder 的修复是必需的：本任务中用户在 worker 会话的回复以 <system-reminder> 开头，main 上的实现把它当成注入消息没有记录，worker 因而无法登记答复
CC-S3UserPromptSubmit（worker）检测 [report] 并提示回传保留
CC-S4Stop（主会话）本会话可以持有租约（没有被另一个主会话的有效租约排除、没有让出过租约）时：有未处理的回传、到期未转交的问题或失效的例行会话（attention 的 routine 为 stale，提示给它发消息重新设定）时阻止结束一次；这一轮是用户的 turn（CC-S6）且 attention 的 needs_prestart 非空或例行会话需要启动（missing）时也阻止一次，提示为列出的任务预启动（DN002 §5.6）、启动例行会话（DN006 §8.9.2）。几条原因合在一条提示里，stop_hook_active 时不再阻止保留；预启动提醒为 T244 新增，例行会话提醒为 T243 新增
CC-S5Stop（worker）评审进行中时阻止结束一次；记录 worker.turn_ended保留
CC-S6UserPromptSubmit（主会话）记下这一轮是不是用户本人的 turn：按 CC-S2 的同一规则判断（去掉前置 <system-reminder> 后为空或以注入标记开头的不是），写入数据目录 cache/turns/<会话>.json；Stop 读取后即删除，hook 没有看到开头的一轮（没有 UserPromptSubmit）因此不算用户的 turnT244 新增
CC-S7SessionStart（例行会话）注入例行会话指令（CC006 §6）T243 新增

CC-S4 预启动提醒的背景与 escape：只有用户本人的 turn 能创建会话（CC001 §4）。2026-11-07 主会话登记了等待依赖的任务后，没有在之后的用户 turn 里为它预启动，用户提醒后才补上；之后要等用户再发消息才能创建，依赖链因此停住。Stop hook 本身不知道这一轮由谁触发，所以由 CC-S6 在一轮开始时记下。提醒只在用户的 turn、本会话没有被另一个主会话的有效租约排除（另一个会话持有租约时本会话不能预启动）、列表非空时出现，每轮最多一次。escape：用户要求先不开始、或预启动确实不合适时，主会话说明原因后直接结束（第二次 Stop 带 stop_hook_active，不再阻止）；用户也可以关闭预启动（scheduling.prestart.enabled）。标记只是缓存：写入失败时这一轮不提醒，不影响其他行为（DN008 §8 第 2 条）。

现有校验归类理由

6. 允许规则与 auto 模式规则

用户 2026-11-07 决定：Claude app 的 auto 权限模式由分类器判断每次工具调用是否出自用户意图。它只认对话中用户本人的话，不认 tsw 的配置、账本与任务书，所以把派发 worker（start_session）、主会话代为决定、worker 按 delivery.merge 合并等 tsw 已经把关的动作当作未经授权而拒绝（live host-e2e 中出现）。对 tsw 自己把关的动作，claude-code 生成 Claude Code 的显式允许规则（permissions.allow），由 hooks 守卫与 MCP 工具的授权检查作为这些动作的门禁；其他一切仍由宿主的权限模式与分类器把关。

会话设置文件允许的动作仍然生效的检查
主会话数据目录的 .claude/settings.json（render_instructions 一并生成）tsw MCP 工具；start_session、send_message / SendMessage、stop_session、get_session、list_sessions、archive_sessionCC-B9；tsw 工具按角色、守卫与用户来源校验
worker无（T245 起不生成）。执行目录带自己的设置文件时，即使在已信任的数据目录之下，app 也会为它再次要求信任确认（Claude Code 文档 permissions.md“project allow rules and workspace trust”说的是允许规则；桌面 app 实测对只有 env 与 hooks 的 settings.local.json 同样要求，确认框写明 “Execution allowed by: .claude/settings.local.json”；数据目录中 T241、T245 的执行目录各有一条单独的信任记录，没有规则文件的 T242–T244 没有），每个新任务因此多一次确认。attempt_start 删除早先 tsw 写下、只含 tsw 规则的 settings.local.json；含其他内容（如用户在该会话中放行的规则）的文件不动worker 的 tsw 工具、send_message / SendMessage 由 auto 分类器判断（T242–T244 的 worker 没有允许规则，调用都没有被拦）；合并由用户设置中的“TaskSteward Worker Merge”放行CC-B6、CC-B7；hook 的拒绝优先于一切放行

start_session 与 send_message 等会话工具由 app 自己的分类器把关，不受 permissions.allow 约束（live 中允许规则已生效，带“worker 自行合并”的任务书正文仍被拦截）。用户 2026-11-07 决定：创建 worker 会话时 prompt 只写短指令（角色、attempt、任务书路径），background 只写任务标题、仓库与执行目录，任务书正文（含交付与合并方式）由 worker 从 runs/ 读取；合并的把关点因此在 worker 实际合并时，由 auto 模式规则与 hooks 守卫承担，而不是在创建会话时由 app 分类器判断。会话可能在 attempt_reconcile 之前开始第一轮（whoami 仍为 pending），主会话绑定后发消息通知它。

auto 模式分类器另有自己的规则（autoMode.allow / soft_deny），其中“Merge Without Review”把 worker 合并自己的 PR 判为未经评审的合并（live 中即使命中允许规则的合并也出现过被拒）。Claude Code 只从用户设置、命令行设置与托管设置读取 autoMode，项目设置与本地设置中的一律忽略（Claude Code 2.1.302 中核实），所以 tsw 不能把它与允许规则一起生成：tsw host install-hint 给出三条规则，由用户加入自己的用户设置（用户 2026-11-08 决定：凡是 tsw 已把关、分类器仍会误拦的动作，都用 auto 模式规则在策略层放行）：“TaskSteward Worker Dispatch”（主会话以 attempt_start 返回的会话名与 cwd、只指向任务书的短指令创建 worker 会话；live 中同样的短指令创建曾被分类器以“Blocked by classifier”拒绝一次，用户重试后通过）与“TaskSteward Worker Merge”（限 worker 会话、本任务的 PR、单独的 gh pr merge … -R …，不含 --admin 与绕过检查；不看任务类型），以及“TaskSteward Routine”（限例行会话：按 routine_board 的返回设定、续期自己的定时任务，用 WorkIQ fetch 读取 tsw 指定的 Teams chat（T253 前为 Teams MCP 的 ListChatMessages），把 tsw 生成的消息发给主会话，清空自己的上下文；T243）。worker 的 tsw 工具与发给主会话的消息没有对应的规则：分类器本来就不拦它们（上表）；如果 live 中出现误拦，再按同一原则在 install hint 中加一条覆盖它们的规则。attempt_start 同时返回执行目录在磁盘上的实际写法 cwd：app 拒绝大小写不同的同一目录。

Claude Code 对复合命令（;、&&、管道）逐段核对允许规则，有一段不在规则内就交给权限模式与分类器判断。live 中单独的 gh pr merge … -R … 直接执行，而后面接了 git fetch 等命令的同一合并被分类器以“Merge Without Review”拒绝；worker 指令因此要求合并命令单独运行，auto 模式规则也只描述单独的合并命令。

worker 能写自己的执行目录，所以 CC-B2 拦下编辑类工具对执行目录与数据目录中 .claude/settings*.json 的修改：遇到权限拒绝时不自行添加允许规则，而是告诉用户；在执行目录中写规则还会让下一次在该目录打开会话时要求信任，数据目录中的文件会被 tsw 重新生成覆盖。允许规则只放行动作本身；动作的授权仍由账本、配置与用户来源决定，主会话代答也仍然不是用户批准（DN006 §8.1b）。

  • 其余一切动作仍由 Claude Code 的权限模式与分类器判断：tsw 不放宽它不检查的动作。
  • tsw 不在任何执行目录中写规则，worker 的放行只来自用户设置。“TaskSteward Worker Merge”描述会话目录为数据目录下 work/<任务>/<attempt>，或其中由 tsw 创建的仓库 worktree 的 worker（T251 起规则文本加入后者，CC006 §8；用户设置中的旧规则需按 tsw host install-hint 更新这一条）。执行目录在数据目录之外的 worker 合并时可能被分类器拦下，这类目录也仍需用户在第一次使用时确认信任；需要时由用户在用户设置中为该目录补一条规则，或把执行目录放在 work/ 之下。
