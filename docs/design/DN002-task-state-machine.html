DN002 任务状态机

  • 状态：设计草案（T233 r3）
  • 日期：2026-11-05
  • 相关：DN001 总体架构 · DN003 统一配置 · DN004 worker 自评审 · DN005 历史导入与 resume · DN006 插件层

本文定义 TaskSteward 的任务状态、迁移、触发者、守卫条件和副作用。状态只能通过账本事件改变：每次迁移对应一条带 sequence 的事件，投影和状态页由事件归约得到，模型和页面都不能直接改状态。

1. 状态划分原则

从主会话（orchestrator）的角度划分状态：两个状态之间只有在必须等待“别的事情”发生时才分开。别的事情包括用户澄清或决定、前序任务完成、名额或资源释放、平台创建会话、worker 执行、外部条件恢复。主会话自己立刻就能完成的步骤（规划、准备 worktree、生成任务书、核验）不单独成为状态，而是作为迁移的副作用。

按此原则，相对第 1 版合并了以下状态：

第 1 版状态本版理由
pending（登记未规划）intake 待受理登记到规划之间唯一需要等的是用户澄清，因此只保留一个“待受理”状态：有待澄清问题就停在这里，否则主会话直接规划离开
preparing + dispatchingdispatching 派发中准备执行目录和任务书是主会话的即时动作；真正需要等的是平台创建会话、用户点击启动提案或对账
submitted + integrating + conflictverifying 主控核验都由主会话持有：核验、集成、组合验证。冲突需要 worker 解决时回到 in_progress（T17），不另设冲突状态
failedpaused（类别 failure）失败与暂停都是“worker 已停、名额释放、等条件恢复”，处理方式相同；页面用类别标签区分
attempt 状态机（独立图）attempt 阶段属性（§6）会话创建、对账、提案、停止、丢失都已体现为任务迁移的守卫和副作用，不再单独成图

2. 状态定义

状态中文标签含义占用名额终态可 resume
intake待受理已登记（新建、导入未规划、退回或需求变更后），等待主会话受理；有待澄清问题时停留否否是
waiting_dependency等待依赖已规划，至少一个依赖未满足否否是
ready就绪依赖满足，等待名额、资源、租约或派发窗口否否是
dispatching派发中执行目录与任务书已就绪，正在创建或续用 worker 子会话是否是
in_progress执行中worker 持有任务；内部子状态见 §3.3是否是
waiting_user等待用户worker 提问或评审受阻，等待用户答复；子会话保持是否是
paused暂停worker 已停；带 owner / next_action / resume_condition / 类别否否是
verifying主控核验worker 已提交终版与评审证据，主会话核验、集成、组合验证是否是
done完成·待用户验收主会话已技术验收，等待用户人工验收否否是（仅验收或退回）
accepted已验收用户已验收当前 revision；只读否否否
cancelled已取消用户删除或关闭；只读否否（可归档）否
archived已归档退役，禁止复用其 agent 和会话否是否

paused 的类别：external（外部依赖）、user_park（用户明确搁置）、failure（已核实失败）、workdir_conflict（现场冲突待决定）、integration_blocked（集成或验证受阻）、import_handover（导入的活动任务待核实旧 worker 停止）。

3.3 执行中的 worker 内部子状态

in_progress 内部的子状态由 worker 推进，主会话不介入，只通过 G-SUBMIT 复核结果。自评审流程见 DN004。

ID从到事件守卫 / 说明
E01executingreviewingreview.started成果已提交到 Git（代码 / 设计）或报告草稿已写入（研究）；本周期轮次 < 本周期预算（否则交主会话判断）；按 R-ROUND 递增计数
E02reviewingreviewingreview.failed调用失败或超时，本轮重试次数 < review.retry_limit；超限时记录 review.unavailable 交主会话判断（可改用 fallback_session、稍后重试或经 T11 交给人类，不能跳过评审）
E03reviewingtriagingreview.completed评审器返回符合 schema 的 JSON（verdict + findings）
E04triagingrevisingreview.decision=iterate有需修复的阻断项，且本周期轮次 < 本周期预算；预算用完时交主会话判断，主会话追加轮次后同样经 E04 继续
E05revisingreviewingreview.started新 HEAD 已提交；本周期轮次 < 本周期预算；按 R-ROUND 递增计数；增量评审（同一评审线程续用，范围为上轮 HEAD..新 HEAD）
E06triagingexecutingworker.self_check_failed自查发现遗漏（验收项未完成、报告缺失），或定稿后 HEAD 有变化需要补审；不开启新周期
E07executing、reviewing、triaging、revisingexecutingtask.requirement_changed主会话转达新 revision；进行中的评审中止，旧评审对新 revision 失效；开启新提交周期

triaging 中 worker 决定 finalize（每个阻断项都已按 G-SUBMIT 处置，且终版 HEAD 已评审）后，直接经 T13 离开 in_progress。定稿后若 HEAD 又有变化（例如修正报告链接），需对差异再评审一轮，经 E06 → E01，同样受本周期预算限制。阻断项需要延后、或修复超出本任务范围时，worker 不能自行 defer，而是记录 review.defer_requested 交主会话判断：主会话可以批准延后（列入已知问题）、要求继续修复，或交给人类。

R-ROUND（评审计数）：每条 review.started 事件在同一事件中原子地把轮次编号设为该 attempt 上一轮编号 + 1（首轮为 1），并把本周期轮次计数 + 1；E02 重试只增加本轮重试计数，不增加轮次。

评审预算：所有新评审轮次（E01、E05）都先检查本周期轮次 < 本周期有效预算。有效预算 = max_rounds + 主会话追加 + 用户追加，两种追加分别记账：

  • 主会话追加：review.budget_extended（source=orchestrator），同一周期累计不超过 orchestrator_extension_limit；
  • 用户追加：review.budget_extended（source=user，附 VerifiedSource），由用户在交给人类的请求中批准，每次写明追加轮数，没有累计上限；它通过 T12 返回，周期与轮次编号都不重置。

预算用完仍有阻断项时，worker 记录 review.budget_exhausted，由主会话判断（DN006 §8.3）：追加轮次、认定意见不成立、批准延后、调整方向，或经 T11 交给人类。主会话判断期间任务保持 in_progress、名额保持，worker 会话等待决定。主会话选择“调整方向”时不增加预算：worker 按新方向修改后，下一轮评审仍须满足预算守卫，预算不足时须另有追加决定。

提交周期：每次经 T08、T17、T20 进入 in_progress，或发生 E07、或 T12 返回时 revision 已变化，开启新周期，到 T13 提交结束；revision 未变的 T12 与 E06 不开启新周期。max_rounds 按周期计算；轮次编号在整个 attempt 内单调递增、唯一，便于引用评审文件。

3.3a 主会话判断

worker 提问（worker.question）、评审预算用完（review.budget_exhausted）、阻断项延后请求（review.defer_requested）、评审器不可用（review.unavailable）时，任务保持 in_progress，由主会话判断（DN006 §8）。主会话在授权边界内自行处理时记录相应决定（回答、追加轮次、认定意见不成立、批准延后、调整方向），附理由与依据，任务状态不变；只有决定交给人类时才记录 input.escalated 并经 T11 进入 waiting_user。判断是主会话的即时工作，按 §1 的原则不单独成为状态。

3.4 导入映射（不在状态图中）

从 orchestrator-agent 导入的任务不经过 T01，而是由导入事件直接落到下表的状态，按 I01 → I02 → I03 → I04 → I05 → I06 的顺序判定，先命中先生效，各规则互斥。分类流程图与细节见 DN005。

4. 守卫条件

守卫定义
G-PLAN任务书字段完整；类型为 研究 / 设计 / 代码 之一；仓库 ID 在配置中存在
G-DEP每个依赖都满足：(1) 状态为 done、accepted，或 archived 且退役前为 done / accepted（非取消归档）；(2) 被依赖的 revision 等于该任务的当前 revision，且其完成证据属于这个 revision（归档不会让旧 revision 重新有效）；(3) 没有未解决的 stale 标记。cancelled 与取消归档的任务永远不满足。在 T04、T05、T07、T20 和 G-ACCEPT 中复核
G-LEASE当前主会话持有调度租约（DN001 §6.4）
G-SLOT占用名额的任务数（dispatching + in_progress + waiting_user + verifying）< scheduling.max_workers；检查与占用在同一事件中原子完成
G-RES任务声明的独占资源没有其他任务未释放的占用记录；本任务自己保留的占用可直接续用（幂等，不重复建立）。占用在首次 T07 建立，只在释放事件时解除（T18 完成、取消后核实停止、resource.released）；暂停、失败、停止事实未知、退役保留的占用都继续有效
G-WINDOW当前 turn 允许启动会话（DN001 §6.3）。只在会话适配器声明 dispatch_window=true 时适用（DN006 §7.3）。不满足时 T07 仍可进行，但创建改为提案卡片，任务停在 dispatching 等用户点击
G-ONE-ATTEMPT该任务没有其他处于 starting / live / stopped 阶段的 attempt
G-PAUSE记录了 owner、next_action、resume_condition 和类别
G-SUBMIT以下均针对当前 revision 与当前提交周期：报告的 md 与 html 都存在；本周期至少完成一轮由 roles.reviewer.session 指定的只读评审器（默认 Codex gpt-6-astra / medium）给出的评审；最后一轮评审的 HEAD 等于提交 HEAD；最后的评审决定为 finalize；每个阻断项都已处置：fix（已验证）、有据 reject、主会话认定不成立（review.finding_overruled），或经主会话 / 用户批准延后（review.defer_approved，且列入报告“已知问题”）；工作树干净或差异已说明。评审为必经环节，不能由配置或主会话关闭
G-ACCEPT当前 revision；验收要求逐项为“已完成 / 用户明确替代”，并附证据；评审证据通过 G-SUBMIT 复核；G-DEP 复核通过；PR 与产出已登记；Git 状态与提交 SHA 已核对；需要集成的仓库已完成集成与组合验证；无待答输入
G-USER来源是统一的 VerifiedSource（DN006 §8.5）：渠道、已核实的用户身份、消息引用、用户原话、所答请求（可空）、决定对象（任务、revision、决定类别）。主会话消息、子会话消息、Teams 回复、Portal 提交都可以满足，只要身份核实为用户本人且决定对象与当前 revision 一致；主会话代答、worker 回执、主控自评与超时都不满足

5. 跨状态规则

5.1 需求变更

用户实质修改任务需求时记录 task.requirement_changed，revision+1。在不同状态下的处理如下：

当前状态处理
intake / waiting_dependency / ready / paused / waiting_user状态不变，任务书 revision 更新；必要时主会话重新规划依赖（记录 dependency.rebound，可能经 T06 / T05）；恢复执行时 worker 读取新 brief；paused 且 resume_target=verifying 时提交证据失效，只能经 T21 / T20 恢复
dispatching状态不变，brief 在绑定前更新到新 revision
in_progress状态不变，子状态回到 executing（E07），旧评审失效，开启新周期
verifying撤回提交，回到 in_progress（T17）
done回到 intake（T23）
accepted / cancelled / archived不接受修改；新建关联任务（新 ID），引用原成果

5.2 依赖失效

上游 revision 增加（T23）或上游被取消（T25）时，系统对每个下游任务记录 dependency.invalidated：

  • ready → waiting_dependency（T06）；
  • dispatching / in_progress / waiting_user / verifying → waiting_dependency（T16），worker 先停止；
  • intake / paused / waiting_dependency：状态不变，恢复或规划时由 G-DEP 拦截；
  • done：标记 stale，并生成待用户决定的输入请求，不自动迁移。用户选择“保持”时记录 dependency.stale_cleared（附用户来源，说明为何旧成果仍然有效）；选择“重新验证”时经 T23 回到 intake（revision+1）。未解决的 stale 使该任务不满足 G-DEP，因此失效会继续向它的下游传播；
  • accepted 及只读任务：不受影响。

5.3 恢复分支选择

resume 命令只产生一条迁移，按以下顺序选择第一个满足的分支：

  1. resume_target=verifying 且冻结的提交证据仍有效 → T27（回到 verifying，不打扰 worker）；
  2. 原子会话可用且可控，且有名额 → T20（回到 in_progress）；
  3. 其他情况 → T21（回到 ready，按 R-ATTEMPT 重新派发）。

因此 T20、T21、T27 的守卫互斥。

5.4 迟到的会话创建

每次请求创建会话（attempt.start_requested）都把该 attempt 的创建代次 gen 加 1，会话名为 txxx-aN-gK（K = 当次代次），并把该代次记为有效。代次一旦被放弃就记为失效：T09（确认未创建或提案过期 / 撤回）、T16 离开 dispatching 时撤回提案，都在同一事件中把当前代次标为失效（attempt.not_created / attempt.proposal_expired 携带代次号）。绑定（T08）只接受当前代次且仍有效的会话。平台出现任何失效代次（包括刚放弃、尚未重试的当前代次）或更早代次的同 attempt 会话时，主会话记录 attempt.late_session，立即停止该会话，不绑定、不发送任务书；当前有效代次的合法会话与任务状态都不受影响。

5.5 R-ATTEMPT：重新派发时的 attempt 规则

任务从 ready 再次派发（T07）时：

原 attempt 情况处理
没有原 attempt新建 attempt a1
planned（从未产生会话）沿用同一 attempt 编号，创建代次 +1 后重新请求创建
starting / proposed不能重新派发：任务仍在 dispatching，须先对账或等提案结果；只有经 T09 回到 planned 后才可再次派发
live 或 stopped，执行目录有效，且由当前主会话启动（可控）续用原 attempt 与原子会话：stopped 先经平台恢复为 live，再发送带新 brief 的消息（attempt.continued），不调用 start_session
live 或 stopped，但由旧主会话启动（接管后不可控，DN001 §6.4）不发消息；核实旧会话已停止、执行目录无新写入后记为 replaced，新建 attempt aN+1 复用同一执行目录
replaced / closed，或导入的旧 Codex / Copilot worker新建 attempt aN+1 复用同一执行目录（导入交接须已有停止证据）

因此 G-ONE-ATTEMPT 始终成立，同一任务不会同时有两个 worker 写同一现场。

6. attempt 阶段（属性）

attempt 是一次执行尝试 Txxx-aN，绑定一个子会话和一个执行目录。它的阶段是任务状态的属性，不另成状态机：

阶段含义出现在任务状态进入方式
planned已生成 attempt 与 brief，尚未请求创建会话（或确认当前代次未创建会话后回退至此）dispatching、readyT07 新建；T09 回退
starting已落账 attempt.start_requested（创建代次 +1）并调用 start_session；结果未知时按当前代次的会话名对账（list_sessions {linked:true}），绝不再次创建dispatching调用工具前
proposed平台拒绝在当前 turn 启动会话，已生成提案卡片；用户点击后进入 live，过期或撤回后经 T09 回到 planneddispatchingG-WINDOW 不满足
live子会话存在且绑定；平台事实 working / idle / awaiting_input 只作观察，不改变任务状态in_progress、waiting_user、verifying（续用时也可在 ready、waiting_dependency 中保持）T08、attempt.continued
stopped子会话被停止但仍存在；可控时可续用paused、ready、waiting_dependencystop_session 或用户停止
replaced已核实停止，由新 attempt 接手同一执行目录—R-ATTEMPT、T15
closed任务验收或归档后按配置处置会话（须有工具回执）done、accepted、archivedT18 之后、T24

8. 不变量

  1. 状态只能由事件归约改变；投影、STATUS.html 和任何模型输出都不能直接写状态。
  2. 每个任务至多一个处于 starting / live / stopped 的 attempt；每个 attempt 只绑定一个子会话，子会话不跨任务复用。
  3. 进入 verifying 必须满足 G-SUBMIT。评审器不可用时由主会话判断（改用回退评审器、稍后重试或交给人类），任何情况下都不能跳过评审。需求变更会把 verifying 撤回到 in_progress（T17），因此不存在“已提交但评审已失效”的状态。
  4. done 必有主会话写的 review.md 与逐项验收结论；accepted 必有 G-USER 来源。
  5. accepted 只能迁移到 archived；archived 不可变；只读导入的任务不能产生 attempt。
  6. revision 增加时，旧 revision 的评审与主控验收全部失效，并向下游传播 dependency.invalidated（§5.2）。
  7. worker 一轮结束、子会话 idle、平台通知、超时都不是完成、批准或答复。
  8. 占用名额的状态恰为 dispatching、in_progress、waiting_user、verifying。
  9. 不对可执行文件做哈希；交付物身份使用 Git 提交 SHA、PR 与报告内容摘要（非可执行文件）。
