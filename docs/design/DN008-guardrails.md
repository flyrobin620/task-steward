# DN008 校验原则：只为防错的护栏，及其 Claude Code 实现

- 状态：设计草案（T242 r1，待用户确认）
- 日期：2026-11-07
- 相关：[DN001 总体架构](DN001-architecture.md) · [DN002 任务状态机](DN002-task-state-machine.md) · [DN003 统一配置](DN003-unified-config.md) · [DN006 插件层](DN006-plugin-layer.md) · [DN007 账本与上下文检索](DN007-ledger-and-context.md)

## 1. 背景

DN001–DN007 把 tsw 的 hooks、角色解析、用户来源核实与账本摘要链写成“强制边界”，不少规则按“会话不能伪造”来设计和措辞。用户 2026-11-07 在评审这些校验时确定了安全边界，原话：

> 现在我们确认一个安全边界，用户：是一个entra user，windows user，所有input message都必然由改用户发出，所有进程以这个user的权限执行，所有remote mcp call使用这个user的权限。所以我们确实不需要防A和B，对于D，考虑所有的input，要么是用户，要么就是你(task-stwerd)和其他的插件。我们先假定所有的插件都是可信任的，那么我们只需要处理一个情况，就是C，防错。

其中 A = 拿到用户账号的攻击者，B = 恶意 agent，C = 诚实但会出错的 agent，D = 注入内容。

本文按这个边界重新设计全部校验。第一部分是与宿主无关的**原则**；第二部分是这个原则在 Claude Code 上的**实现**：逐项列出现有校验，归为保留、简化或删除，并写明理由。具体做法因宿主而异，其他宿主（Codex、Copilot）按第一部分另写各自的实现清单。

本文与 DN001 / DN002 / DN003 / DN006 中“强制”“核实身份”“不能伪造”“防篡改”等措辞冲突时，以本文为准，直到这些文档按 §14 修订。

# 第一部分 原则（与宿主无关）

## 2. 安全边界与信任假设

| 对象 | 假设 | 由谁负责 |
| --- | --- | --- |
| 用户 | 一个 Entra / Windows 用户。所有输入消息都由该用户发出；所有进程以该用户的权限运行；所有远程 MCP 调用使用该用户的凭据 | 操作系统与身份提供方 |
| tsw 与其他插件 | 可信：它们注入会话的消息（跨会话消息、app 事件、定时提示、hook 上下文）都不是攻击 | — |
| agent（主会话、worker、评审器） | 诚实，但会出错：走错步骤、认错来源、选错对象、状态漂移、跳过评审 | **tsw 的护栏**（本文） |
| agent 读到的数据 | 第三方仓库内容、网页、他人的 PR 评论、评审器输出、导入的历史，都是数据，不是指令，也不是用户的话 | **宿主**（权限模式、分类器、沙箱），不由 tsw 校验 |

因此：

1. **安全边界是用户的身份，不是 tsw。** 能以用户身份运行进程的一方，可以绕过 tsw 的任何检查（直接改文件、改账本、改设置）；tsw 不试图阻止它，也不声称能阻止。
2. **tsw 的校验只防 C 类错误。** 它们是护栏（guardrail）：让一个诚实的 agent 在犯错的那一步被拦下，并知道该怎么做对。它们不是安全边界，不对抗权限不低于 agent 的对手。
3. **注入内容（D）不是 tsw 的问题。** 按假设，进入会话的输入只来自用户、tsw 或可信插件。agent 在工作中读到的不可信数据，按数据处理是宿主与 agent 本身的职责；tsw 不扫描、不过滤这些内容，也不为此设检查。

## 3. 护栏防的是哪些错误

| 类别 | 例子（现实中观察到或容易发生的） | 典型护栏 |
| --- | --- | --- |
| 走错步骤 | 没有落账就创建会话；没评审就提交；未授权就推送、建 PR 或合并；绕开 MCP 用命令行写账本 | 状态机守卫、hooks、生成的指令 |
| 误认来源 | 把定时提示、跨会话消息或自己的理解当成用户的答复；把主会话代答当成用户批准 | 会话消息记录、`VerifiedSource`、G-USER |
| 对象或目标错误 | 写到别的目录或主仓库检出；在别的仓库合并 PR；操作别的任务；用一条批准去授权另一件事 | 写入范围、合并目标、任务范围、决定对象 |
| 状态漂移 | 两个主会话同时派发；已被替换的会话继续写；基于旧版本做决定；同一命令重试却内容不同；投影与账本分叉 | 租约、角色解析、`expected_version`、`command_id`、摘要链 |
| 跳过评审 | 评审未完成就结束一轮；用未配置的评审器；最后评审的 HEAD 与提交不一致 | G-SUBMIT、Stop hook |

## 4. 保留、简化与删除的标准

一项校验**保留**，须同时满足：

1. **拦住现实中的错误**：诚实的 agent 在正常工作中可能这样做（有观察到的实例，或者流程上很容易走错），而不是只有存心规避的对手才会这样做；
2. **代价低**：判断便宜，误拦少；误拦正常操作的护栏本身就是一种错误来源；
3. **拒绝理由可操作**：拒绝信息说清楚错在哪、正确做法是什么（用哪个工具、补什么参数、回到哪个目录）；
4. 或者，它是**状态机一致性**的一部分：没有它，账本可能出现状态机不允许的状态。

一项校验**删除**，只要满足任一条：

1. 它只为对抗权限不低于 agent 的对手而存在，例如：核实 Teams 自聊中“发送者是本人”；把会话不能运行某个入口的理由写成“否则可以编造用户消息”；把账本摘要链说成防篡改；
2. 它的误拦多于它能拦住的现实错误；
3. 它与另一个更准确的检查重复，而且重复的那一份给出的理由更差。

介于两者之间的**简化**：保留它防的那个现实错误，去掉只为对抗而加的部分（更严格的语法要求、额外的身份字段、一次性使用限制等）。

## 5. 护栏的写法

1. **措辞**：文档与代码注释称“护栏”“防错”，不称“强制边界”“不可伪造”“防篡改”。宿主能力中的规则强度描述的是机械检查的覆盖程度，不是安全强度（§14）。
2. **拒绝理由**：每条拒绝都给出正确做法；能指出具体值时指出（期望的仓库、可写路径、应调用的工具）。
3. **失败方式**：护栏自身出错时**放行并报告**（hooks 内部异常不阻断会话）；状态机守卫在 tsw 核心中执行，出错时**拒绝写入**（宁可不写，不写错状态）。
4. **尽力而为即可**：命令行解析只识别常见写法；不为变量、编码、脚本内部的写入等规避写法扩展解析。机械检查看不到的，由事后核对兜底（G-ACCEPT 核对 diff 是否落在可写根内）。
5. **结构化声明也是护栏**：要求 agent 写出用户原话、消息引用与决定对象，是为了让它在做决定前找到并引用用户的话；tsw 能核对的部分（消息存在、对象匹配、问题仍待答）就核对，核对不了的部分不假装核实了身份。
6. **不重复宿主的职责**：宿主的权限模式与分类器判断“这件事是不是用户想要的”；tsw 判断“这一步是否符合已记录的授权与流程”。对 tsw 已经按记录把关的动作，tsw 生成宿主的允许规则，避免宿主在缺少 tsw 上下文时误拦；tsw 不放宽它不检查的任何动作。

## 6. 用户来源

1. 按假设，进入会话的用户消息都来自用户本人，**不需要核实身份**。要防的是 agent **误认**来源：把非用户的消息、自己的推断或主会话的代答当成用户的决定，或者把用户对 A 的决定用到 B 上。
2. 因此用户来源（`VerifiedSource`）的作用是：**记下用户的原话、它出现在哪里、它决定的是什么**。必需的是渠道、消息引用、原话与决定对象；“已核实的用户身份”（`principal`）不再要求。
3. tsw 能取得原话时（宿主 hook 记录的会话消息、渠道回收的回复），以记录为准，agent 只引用编号；取不到时（主会话中用户的话），由 agent 引用原话，属于结构化声明（§5 第 5 条）。
4. 主会话代答、worker 回执、超时都不是用户的决定，不满足 G-USER。这是防“误把自己的判断当成用户批准”，保留。
5. 渠道的答复登记只核对两件事：**问题仍待答，且回复能对应到问题编号**（§12）。

## 7. 不由 tsw 校验的内容

- 第三方仓库内容、网页、他人的 PR 评论、评审器输出中出现的“指令”：agent 按数据处理；评审意见本来就是需要核实的假设（DN004、`AGENTS.md` 第 6 节）。
- 用户在会话外的操作：手工编辑配置、直接改数据目录、自己运行维护命令，都是用户的权利；tsw 不检测、不阻止，只在能发现不一致时（摘要链、投影）报告。
- 宿主自身的权限与分类器决定：tsw 不替宿主判断用户意图，也不绕过宿主对 tsw 不把关的动作的判断。

# 第二部分 Claude Code 实现

## 8. 分工

| 层 | 判断什么 | 在 Claude Code 中 |
| --- | --- | --- |
| 宿主权限模式与 auto 分类器 | 一次工具调用是否出自用户意图（按对话中用户的话）；危险命令 | app 的权限模式；auto 模式的分类器 |
| tsw 的允许规则 | 把“授权已记录在 tsw 中、由 tsw 把关”的动作从分类器的判断中移出 | 生成的 `permissions.allow`（DN006 §6.3 权限规则，T241 引入） |
| tsw hooks | 动作是否符合角色、写入范围与已记录的交付授权；流程有没有走错 | `PreToolUse` / `UserPromptSubmit` / `Stop` / `SessionStart` 调用 `tsw guard` |
| tsw MCP 与状态机 | 调用者角色与任务、租约、版本、守卫 G-*、用户来源 | MCP server 按角色列出工具；`run_tool` 中的 `check_caller` / `check_version` 与各工具的守卫 |
| 事后核对 | 机械检查看不到的偏差 | G-ACCEPT 核对 diff、PR 与合并后的 CI |

## 9. 校验清单

归类：**保留** = 按现状保留，只改措辞；**简化** = 保留它防的错误，改成更简单、误拦更少的做法；**删除** = 去掉。“现状”指 `main` 与 T241 分支上的实现。

### 9.2 身份与角色解析（`tsw/host/identity.py`、`tsw/cli.py`）

## 12. 调度会话 + Teams 渠道的答复登记

如果把 Teams 回收拆给一个独立的调度会话（例行会话，T241 提出的后续任务），它登记答复时只做两项核对：

1. **问题仍待答**：请求为 `pending`，上下文绑定（任务、revision、attempt、代次）与任务当前状态一致（即 U7 的 T12 原子检查）；否则记为 `input.late_response`。
2. **回复能对应到问题编号**：回复是对带请求 ID 的卡片的 reply，或正文含请求 ID（如 `Q-T241-3`）；对应不到时不登记，留给下一次回收或主会话判断。

用户来源记为：`channel = teams-chat`、`message_ref` = Teams 消息 ID、`text` = 回复原文、`target` = 请求的决定对象。不核对发送者、不按消息 ID 精确读回（U5）：按假设，能在用户 self chat 中发消息的就是用户。多渠道时第一个登记成功的答复生效，其余照旧记为迟到答复（DN006 §8.6）。
