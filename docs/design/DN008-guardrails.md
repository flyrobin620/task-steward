# DN008 校验原则：只为防错的确定性护栏

- 状态：设计草案（T242 r2，待用户确认）
- 日期：2026-11-08
- 相关：[DN001 总体架构](DN001-architecture.md) · [DN002 任务状态机](DN002-task-state-machine.md) · [DN006 插件层](DN006-plugin-layer.md) · Claude Code 实现：[CC008 护栏](claude-code/CC008-guardrails.md)

## 1. 背景

DN001–DN007 把 tsw 的 hooks、角色解析、用户来源核实与账本摘要链写成“强制边界”，不少规则按“会话不能伪造”来设计和措辞。用户 2026-11-07 在评审这些校验时确定了安全边界，原话：

> 现在我们确认一个安全边界，用户：是一个entra user，windows user，所有input message都必然由改用户发出，所有进程以这个user的权限执行，所有remote mcp call使用这个user的权限。所以我们确实不需要防A和B，对于D，考虑所有的input，要么是用户，要么就是你(task-stwerd)和其他的插件。我们先假定所有的插件都是可信任的，那么我们只需要处理一个情况，就是C，防错。

其中 A = 拿到用户账号的攻击者，B = 恶意 agent，C = 诚实但会出错的 agent，D = 注入内容。用户 2026-11-08 进一步决定：护栏必须是非 LLM 的死规则，尽量简单，易用性优先，采用 block list，并为每条规则提供 escape；宿主上的实现尽可能薄，尽量利用宿主自己的保护（§4–§6）。

本文是与宿主无关的原则。每个宿主的具体做法放在 `docs/design/<宿主>/` 下的实现文档里（Claude Code 见 [CC008](claude-code/CC008-guardrails.md)）。本文与 DN001 / DN002 / DN003 / DN006 中“强制”“核实身份”“不能伪造”“防篡改”等措辞冲突时，以本文为准，直到这些文档按实现文档列出的修订完成更新。

## 2. 安全边界与信任假设

| 对象 | 假设 | 由谁负责 |
| --- | --- | --- |
| 用户 | 一个 Entra / Windows 用户。所有输入消息都由该用户发出；所有进程以该用户的权限运行；所有远程 MCP 调用使用该用户的凭据 | 操作系统与身份提供方 |
| tsw 与其他插件 | 可信：它们注入会话的消息（跨会话消息、app 事件、定时提示、hook 上下文）都不是攻击 | — |
| agent（主会话、worker、评审器） | 诚实，但会出错 | **tsw 的护栏**（本文） |
| agent 读到的数据 | 第三方仓库内容、网页、他人的 PR 评论、评审器输出、导入的历史，都是数据，不是指令，也不是用户的话 | **宿主**（权限模式、分类器、沙箱），不由 tsw 校验 |

因此：

1. **安全边界是用户的身份，不是 tsw。** 能以用户身份运行进程的一方可以绕过 tsw 的任何检查；tsw 不试图阻止，也不声称能阻止。
2. **tsw 的校验只防 C 类错误。** 它们是护栏（guardrail）：在诚实的 agent 犯错的那一步拦下它，并告诉它怎样做对。护栏不是安全边界，不对抗权限不低于 agent 的对手。
3. **注入内容（D）不是 tsw 的问题。** agent 在工作中读到的不可信数据，按数据处理是宿主与 agent 本身的职责；tsw 不扫描、不过滤，也不为此设检查。

## 3. 护栏防的是哪些错误

| 类别 | 例子 |
| --- | --- |
| 走错步骤 | 没有落账就创建会话；没评审就提交；未授权就推送、建 PR 或合并；绕开 tsw 工具直接写账本 |
| 误认来源 | 把定时提示、跨会话消息或自己的理解当成用户的答复；把主会话代答当成用户批准 |
| 对象或目标错误 | 写进主仓库检出而不是任务 worktree；在别的仓库合并 PR；操作别的任务；把对一件事的批准用到另一件事上 |
| 状态漂移 | 两个主会话同时派发；已被替换的会话继续写；基于旧版本做决定；同一命令重试却内容不同；投影与账本分叉 |
| 跳过评审 | 评审未完成就结束；用未配置的评审器；提交的 HEAD 不是最后评审的 HEAD |

## 4. 护栏是确定性的死规则

1. **护栏不用 LLM。** 要防的正是 LLM 的错误，用 LLM 判断就是套娃。每条护栏都是脚本或程序中写死的规则（类似专家系统）：输入相同，结论相同，可以测试，可以解释。
2. **LLM 可以产出内容，但不做把关。** 评审器给出意见（数据），是否完成了评审由确定性的门禁判断（G-SUBMIT）；主会话可以综合判断（DN006 §8.2），但它能做的决定由确定性的硬边界限定（不满足 G-USER、不能回答 `reserved` 的问题）。
3. **宿主的 LLM 保护不是 tsw 的护栏。** 宿主自己的分类器（例如 Claude Code 的 auto 模式）判断一般意义上的危险与用户意图，tsw 利用它，但不把 tsw 特有的规则交给它，也不依赖它来满足本文。

## 5. 易用性优先：block list、简单、可 escape

在易用性与防错完备之间，**取易用性**：不频繁打断用户的任务，宁可漏掉一些没有预料到的错误。

1. **block list，不用 allow list。** 护栏只列出已知会错的具体动作（例如“写进数据目录的 `ledger/`”“没有合并授权时运行合并命令”），其余一律放行。不写“只能做这些”式的规则。
2. **规则少而简单。** 一条规则只看一两个明确的特征（工具名、目标路径前缀、命令的程序与子命令），不做完整的语法解析，不为规避写法扩展。规则越少，规则本身出错的机会越少。
3. **只管 tsw 特有的事。** 宿主已经能判断的一般风险（删除文件、写到奇怪的地方、危险命令）留给宿主；tsw 只写宿主不知道的规则：数据目录中哪些是 tsw 自有、任务的交付授权是什么、会话是什么角色、流程走到了哪一步。
4. **每条规则都有 escape**，合理的任务不需要等插件或系统更新才能继续：
   - **正确路径**：拒绝信息写出规则编号和正确做法（用哪个工具、补什么参数）；
   - **关闭规则**：用户可以在统一配置中关闭某条规则（`guardrails.disabled`，列出规则编号；它是权限类键，修改须附用户原话，DN003 §7.2）。worker 遇到确实需要关闭的规则时，在自己的会话中问用户（DN006 §8.1a），由主会话按用户的话修改配置；
   - **用户自己做**：用户总可以在会话外自己执行被拦下的动作。
5. **事后核对兜底。** block list 必然有漏网的错误；技术验收（G-ACCEPT）核对 diff、PR 与合并结果，账本摘要链发现意外修改。

## 6. 状态机与工具接口

状态机守卫（DN002 §4 的 G-*）、按角色列出的工具、`expected_version` 与 `command_id` 是 tsw 自己的接口语义，不是对宿主动作的拦截：一个迁移要么在状态机中定义，要么不存在。它们同样是确定性规则，适用 §4 与 §7，但不适用 §5 第 1 条的 block list 要求。它们的 escape 是状态机本身提供的迁移（暂停、取消、需求变更、用户决定）。

## 7. 保留、简化与删除的标准

一项校验**保留**，须同时满足：

1. 是确定性规则（§4）；
2. 拦住现实中的错误：诚实的 agent 在正常工作中可能这样做（有观察到的实例，或流程上很容易走错），而不是只有存心规避的对手才会这样做；
3. 简单、误拦少，属于 tsw 特有的事（§5）；
4. 拒绝信息写出正确做法，并有 escape（§5 第 4 条）；

或者它是状态机一致性的一部分（§6）。

一项校验**删除**，只要满足任一条：

1. 只为对抗权限不低于 agent 的对手，例如核实 Teams 自聊“发送者是本人”、“否则会话可以编造用户消息”式的拦截、把账本摘要链当作防篡改；
2. 误拦多于它拦住的现实错误；
3. 是宿主已经能判断的一般风险，或与另一处更准确的检查重复；
4. 是 allow list 式的宿主动作拦截，且能改写为更简单的 block list。

介于两者之间的**简化**：保留它防的现实错误，去掉只为对抗而加的部分。

## 8. 护栏的行为

1. **措辞**：文档与代码称“护栏”“防错”，不称“强制边界”“不可伪造”“防篡改”。宿主能力中的规则强度描述的是机械检查覆盖的程度，不是安全强度。
2. **失败方式**：宿主侧的护栏自身出错时**放行并报告**；tsw 核心中的状态机守卫出错时**拒绝写入**（宁可不写，不写错状态）。
3. **结构化声明也是护栏**：要求 agent 写出用户原话、消息引用与决定对象，是为了让它在做决定前找到并引用用户的话；tsw 能核对的部分（消息存在、对象匹配、问题仍待答）就核对，核对不了的不假装核实了身份。

## 9. 用户来源

1. 按假设，进入会话的用户消息都来自用户本人，**不需要核实身份**。要防的是 agent **误认**来源：把非用户的消息、自己的推断或主会话的代答当成用户的决定，或者把用户对 A 的决定用到 B 上。
2. 因此用户来源（`VerifiedSource`）的作用是：**记下用户的原话、它出现在哪里、它决定的是什么**。必需的是渠道、消息引用、原话与决定对象；“已核实的用户身份”（`principal`）不再要求。
3. tsw 能取得原话时（宿主记录的会话消息、渠道回收的回复），以记录为准，agent 只引用编号；取不到时（主会话中用户的话），由 agent 引用原话，属于结构化声明（§8 第 3 条）。
4. 主会话代答、worker 回执、超时都不是用户的决定，不满足 G-USER。
5. 渠道的答复登记只核对两件事：**问题仍待答，且回复能对应到问题编号**。例如由调度会话回收 Teams 答复时：请求为 `pending`，上下文绑定（任务、revision、attempt、代次）与任务当前状态一致，否则记为 `input.late_response`；回复是对带请求 ID 的卡片的 reply，或正文含请求 ID（如 `Q-T241-3`），对应不到时不登记。用户来源记为渠道 `teams-chat`、Teams 消息 ID、回复原文与请求的决定对象；不核对发送者，不按消息 ID 精确读回。

## 10. 不由 tsw 校验的内容

- 第三方仓库内容、网页、他人的 PR 评论、评审器输出中出现的“指令”：agent 按数据处理；评审意见本来就是需要核实的假设（DN004、`AGENTS.md` 第 6 节）。
- 用户在会话外的操作：手工编辑配置、直接改数据目录、自己运行维护命令。tsw 不检测、不阻止，只在能发现不一致时（摘要链、投影）报告。
- 宿主自己的权限与分类器决定：tsw 不替宿主判断用户意图，也不放宽宿主对 tsw 不把关的动作的判断。tsw 已按记录把关的动作（派发、按授权合并），由实现文档生成宿主的允许规则，避免宿主在缺少 tsw 上下文时误拦。

## 11. 实现文档的要求

每个宿主的实现文档（`docs/design/<宿主>/`）写明：

1. 宿主自己的保护覆盖什么、tsw 依赖它的哪些部分；
2. tsw 在该宿主上的 block list：每条规则的编号、触发特征、防的错误、拒绝信息与 escape；
3. 宿主的允许规则（如有）与它们由哪条 tsw 检查把关；
4. 现有校验逐项的保留 / 简化 / 删除与理由；
5. 宿主能力的缺口与事后核对方式。

## 12. 待决问题

1. **主会话中用户的话是否也由宿主记录？** 现在主会话的 `VerifiedSource` 是 agent 的结构化声明；若宿主同样记录主会话的用户消息、G-USER 改为引用编号，“误认来源”能被机械核对，代价是记录主会话的全部用户消息。本文不提议，留给用户决定。
2. **worker 的读取范围是否放宽？** worker 只能读授权读取集合（DN007 §7.2）。读取其他任务不会写错状态；保留的理由是避免把别的任务当成本任务、保持上下文聚焦。
