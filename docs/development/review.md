# 评审、PR 与合并

开 PR、评审 PR 或回复评审意见时，读本文。

## 评审

- PR 一开就启动独立评审，与 CI 并行；串行会让等待时间翻倍。
- 评审者使用与作者不同的模型：同一模型有相同的盲点。默认评审器是 Codex `gpt-6-astra`（推理强度
  medium，只读沙箱），与 TaskSteward 自己的 worker 自评审一致（DN004）；作者本身是 Codex 时改用
  Claude 只读评审（`claude -p`，调用约定见 DN004 §3.3）。
- 评审请求写明意图、必须保持的不变量、刻意的取舍，以及评审的提交 SHA，避免取舍被当作问题反复提出。
- 评审意见是假设。核对：
  - 能否经受支持的入口触发，包括它需要的并发、失败或恢复序列；
  - 对用户或运行的影响，以及证据。区分实际发生的事故、复现的失败和静态推理；人为构造的测试不能
    证明生产影响，没有发生过事故也不能否定可达的缺陷；
  - 最小的充分修复，权衡复杂度、I/O 与维护成本。
- 修复确认的问题，或写明约束与理由后拒绝。每条意见都要回复；只有处理完的意见才能标记为已解决。
- 评审以 head 提交为准，对较早推送的评审不算数。修复后对最终 head 做增量评审，直到没有未处理的
  意见。
- 意见陆续到达时陆续处理；修完所有已知问题，重跑本地门禁，然后一次推送。

## PR 模板

模板在 [`.github/pull_request_template.md`](../../.github/pull_request_template.md)：意图（含 use case
与迁移编号）、设计、验证表（层级 / 是否运行 / 结果，注明真实或模拟）、未验证项、安全与身份影响、
兼容性、发布与回滚。

## 合并

- `main` 受保护：禁止直接推送，必需检查 `Gate`，必须解决所有对话，合并前分支必须基于最新 `main`。
- 合并方式为 squash；PR 标题用英文，格式 `<area>: <summary>`。
- agent 在以下条件全部满足时合并：`Gate` 在最终 head 上为绿；最终 head 的评审通过；所有意见已回复
  并解决；由编排器派发的任务已经编排者验收。
- 需要用户明确确认才能合并的改动范围见 AGENTS.md 第 4 节。确认须来自用户本人（PR 评论、批准或
  对话中的明确答复），并在 PR 中记录来源；编排者或 worker 的判断不能代替。
- 仓库所有者可以绕过保护规则，仅用于紧急修复，并在 PR 中写明原因。
