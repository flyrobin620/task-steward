# 开发流程：门禁、证据与失败处理

规划一项改动如何从代码走到验证完成，或某一步失败时，读本文。[AGENTS.md](../../AGENTS.md) 第 4 节是
简版。

| 步骤 | 门禁 | 证据 | 失败时 |
| --- | --- | --- | --- |
| 设计（行为变化时） | 相关 DN 已更新并经用户确认 | 设计 PR 或同一 PR 中的 DN 改动 | 先停在设计，不写实现 |
| 代码 + 测试 | 同一改动里新增或更新测试；use-case 目录与状态迁移清单同步 | 测试结果 | 推送前修好 |
| 本地门禁 | lint、类型检查、标准库依赖检查、文档检查、目录检查、unit / component / surface / conformance 全绿 | `tools/gate.py` 的输出与结果文件 | 绝不推送红的门禁 |
| live 场景（按需） | 触及宿主集成、会话适配器或评审协议时，对应场景在最终 head 上通过 | live 运行清单、结果与清理证据 | 修复后重跑；清理按清单收尾 |
| PR | 模板填写完整 | PR 正文 | — |
| 评审（与 CI 并行） | 最终 head 上评审通过；每条意见已回复并解决 | 评审记录 | 修复或说明理由拒绝；重跑本地门禁后一次推送 |
| CI | 汇总检查 `Gate` 为绿 | CI 运行链接与产物 | 先读失败原因再推送 |
| 编排者验收（由编排器派发时） | 编排者逐项核对验收标准 | 验收记录 | 按反馈继续同一任务 |
| 合并 | 以上全部满足；需要用户确认的改动已取得确认（AGENTS.md 第 4 节） | 合并提交 SHA；用户确认的来源 | — |
| 合并后 | `main` 上该合并提交的 CI 通过 | CI 运行链接 | 立即修复或 revert，改动未完成 |

## 门禁建立前的过渡规则

`tools/gate.py` 与 `.github/workflows/ci.yml` 由第一个开发 PR 实现。在它们合并之前：

- 只允许不含运行代码的 PR（规范、设计、文档）合并。合并条件：最终 head 的独立评审通过、意见全部
  解决、已有的检查（相对链接、`git diff --check`、隐私扫描）通过，并取得用户明确确认。
- 第一个开发 PR 同时引入门禁与 CI。它必须在自己的最终 head 上让新建的 `Gate` 为绿，并满足上表的其他
  条件，还要取得用户确认（它改动了 `.github/**`）。
- 该 PR 合并、`main` 上的 `Gate` 第一次为绿后，过渡规则终止，所有 PR 按上表执行；随后为 `main` 启用
  保护规则（见 [review.md](review.md)）。

## 说明

- 修完所有已知问题后再一次推送。每次推送都会重新跑整条流水线，也会让之前的评审失效。
- 合并前分支必须基于最新 `main`（squash 后的内容与通过门禁的 head 一致）。
- 明确写出没有验证的部分。它描述的是完成的改动无法覆盖的范围，不是提前停下的理由。
- 由编排器派发的任务，人工验收在合并后按任务流程进行；合并不代表用户已验收。
