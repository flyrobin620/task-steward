# 0003 worker 走完交付闭环：按仓库授权合并，等主分支 CI 后再提交

- 状态：已接受（2026-11-08，以用户确认合并本 PR 为准）
- 取代：[0002](0002-worker-merges.md) 中合并授权的范围、合并后核对由谁做、须用户确认的改动类别；0002 的其余部分（worker 自己合并自己的 PR）不变，在下面重述
- 适用：本仓库的全部 PR，包括由 TaskSteward 编排器派发的任务

## 背景

0002 让开发任务的 worker 自己合并 PR，但留下两处要主会话代劳：合并授权只对开发任务（kind `code`）成立，设计任务 T242 因此由主会话合并并等待 CI；`main` 上合并提交的 CI 留给主会话在“合并后核对”中检查，T241 提交时 CI 仍在运行，由主会话等待。这与 0002 想要的“主会话保持上下文干净”相反。另外，须用户确认才能合并的类别较宽，每个任务的设计或规则文字在评审修改后还要再次确认，打断较多。

## 决定

替代 0002 的决定（0001 第 7 条的现行文本）：

7. **合并**：squash 合并。`Gate` 在最终 head 上为绿、最终 head 的评审通过、每条评审意见都已回复并解决后，由完成改动的 agent 合并；由编排器派发的任务即由 worker 合并，**不论任务类型**（开发、设计、文档、研究），只要仓库授权 worker 合并（TaskSteward 中为 `repositories.<id>.delivery.merge`）；任务书或仓库 `AGENTS.md` 另有规定时从其规定，提交时写明原因。
   - **交付闭环由 worker 走完**：合并后，worker 等 `main` 上合并提交的 CI 通过；失败时在同一任务内修复（新的 PR，同样评审后合并）或 revert，不能带着失败提交。仓库规则要求的 live 场景在最终 head 上运行；只有在合并后的 `main` 上才能验证的（例如要更新插件或重新生成宿主文件才生效的宿主改动），合并后由 worker 运行。不能运行的写明原因。worker 提交时附合并提交、CI 运行链接与 live 证据；编排者只核对这些证据，不再自己等待 CI。合并不代表用户已验收。
   - **须用户确认才能合并的改动**只剩两类：规则文档与决定记录（`AGENTS.md`、`CLAUDE.md`、`docs/development/**`、`docs/decisions/**`），以及设计文档（`docs/design/**`）。CI 与门禁、发布与版本配置、权限与身份校验相关代码、`LICENSE` 不再单独要求用户确认，由独立评审与门禁把关。确认须来自用户本人，worker 在自己的会话中直接问用户，并在 PR 中记录来源与范围。
   - **一个任务确认一次**：一个任务的设计 / 规则文字经用户确认后，评审或 PR 意见引起的后续修改不再重新请用户确认。例外：新增或删除护栏规则（DN008 / CC008 的 block list 条目），或改变已确认的决定，这类修改仍须再次确认。

0001 的其他各条不变。

## 后果

- `AGENTS.md` 第 4 节、[workflow.md](../development/workflow.md) 与 [review.md](../development/review.md) 按本决定修改，并记入 [instructions-log.md](../development/instructions-log.md)。
- TaskSteward 的状态机（DN002 §3.5、G-SUBMIT、G-ACCEPT）随之修改：合并授权只看仓库；worker 合并的任务提交时须附 `main` 上合并提交的 CI 结果（通过）与 live 说明，CI 未完成或失败时 `submit` 被拒并写明下一步；主会话的 G-ACCEPT 只核对这些证据。
- worker 的执行目录不再带权限规则（带规则的目录即使在已信任的数据目录之下也会再次要求信任）；worker 需要的放行由用户设置中的 auto 模式规则承担（`tsw host install-hint`，[CC008](../design/claude-code/CC008-guardrails.md) §6）。
- 合并后发现的问题以新的 PR 修复或 revert，不改写已合并的历史。
