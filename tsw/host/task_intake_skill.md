# 受理与写任务书

本 skill 只适用于主会话（`whoami` 的角色为 orchestrator）；worker 与例行会话忽略它。调度流程（预启动、派发、回传、核验与验收）见 `orchestrate` skill。

任务书 `runs/<任务>/<attempt>/brief.md` 由两部分组成：tsw 生成的标题、仓库、交付、live、“仓库与 worktree”一节与 resume 资料；以及你在登记与修改时写的目标与验收。后者是任务唯一可靠的记录：会话上下文随时可能丢失，worker 只读任务书。tsw 生成的部分不要在目标里重复。

## 检索历史（DN007）

不要凭会话记忆判断相关任务：会话上下文会丢失，`task_list` 只有标题。按层读取，读得少、找得准：

1. 先完整理解当前请求（与任务书）。
2. `context_catalog` 在同仓库（`repo`，可用别名）或项目范围检索，`query` 写模块、接口、现象、方案名等具体词；请求或任务书中提到的任务 ID 放进 `task_ids`（它们与其硬依赖总在 `pinned` 中）。卡片的 `keyword_source` 为 `generated`、或 `stale` 为 true 时关键词不可靠，结合标题与摘要判断；`next_offset` 不为空表示还有更多。
3. `context_decisions` 按主题词查用户既有的决定与偏好：只有 `usable_as_basis` 为 `in_scope` 的长期偏好能直接作为依据；`this_task_only` 在其他任务中只能作为先例参考；`false`（已被替代、候选约定）不能作为依据。
4. 只对入围的任务 `context_read` 需要的部分（spec / report / decisions / reviews / outputs 等），`reason` 写明为什么读；核验与验收时用 `context_task` 看本任务的完整过程。
5. 有具体缺口时再扩大：`scope: global`（写 `reason`）或 `context_search` 全文检索（少于 3 个字的词只在卡片上匹配）。
6. 判断、规划与验收的依据引用卡片或原文出处（任务 ID、文件、事件序号）。

索引是可重建的缓存：结果带 `index_lag` 时部分任务只按标题与仓库参与；损坏或明显过期时 `context_rebuild`。

## 受理

- 受理新任务前先按“检索历史”在同仓库 / 项目范围查：是否与已有任务重复、相关任务与可复用的成果、可能的依赖、用户在类似问题上的既有决定；把查到的相关任务与理由告诉用户，重复或依赖由用户确认后再登记或规划。
- 登记：`task_register`：
  - `title`：`[仓库或项目简称] 摘要`，例如 `[tsw] …`；
  - `repo`、`kind`（`code` / `design` / `research`）；
  - `goal` 与 `acceptance` 按下面两节写。
- 随后 `task_summary`（`stage: intake`）按任务书写 4–8 个具体关键词（模块、接口、现象、方案名，不写“实现”“修复”这类泛词）。
- 目标、范围或验收有疑问时 `intake_question`，用户答复后 `input_resolve`（附用户原话的 `user_source`，`request_id` 指向该问题）。

## 目标的写法

按以下顺序分节写：

1. **用户原话**：开头写日期与会话（例如“用户 2026-11-14 在主会话中的原话（按顺序）：”），逐条引用用户关于这件事说过的话；你的答复与用户对它的回应也按顺序写入（例如“主会话答复：…。用户：‘拆出 skill’”）。不改写、不概括用户原话。
2. **背景（主会话核实）**：你核实过的事实（命令输出、配置、文档章节）、相关任务及出处（任务 ID、follow-up 编号）、适用的用户决定与偏好、约束（例如“权限类配置只能由主会话按用户原话写入”）。
3. **要做的**：编号的工作项，每项写清楚对象与范围。
4. **并行**：同时执行、可能改到相同文件或资源的任务及分工；没有时写“无其他执行中的任务改动这些文件”。

另外按情况写明：

- **设计确认**：会改变已定义的行为、按仓库规则需要先改设计的，写明“设计写入相关文档，按仓库规则需用户确认后再实现与合并”。
- **用户授权**：只写用户说过的授权，附原话与范围，例如“用户授权过夜进行：‘……’（设计与合并无需再确认，范围限于本任务）”。没有原话就不写，也不代为授权。主会话的决定不是用户批准。

## 验收的写法

- 每条都能逐项核对：写明对象与证据（哪个文件、哪条命令、哪个测试层级、哪个链接），不写“质量好”“完善”这类无法核对的话。
- 交付方式（推送、PR、合并）与 live 规则由 tsw 按仓库配置写在任务书开头，不在验收中重复；本任务有特别要求时（例如“本任务不合并”“合并后由主会话下一次派发核对”）才写。
- 报告的形式写在最后一条，例如“交付中文报告 runs/<任务>/<attempt>/result.md 与 HTML”。

## 交流语言（DN003 §3.5a）

- 用户偏好的交流语言保存在统一配置 `control.language`（BCP 47 标签，默认 `zh-CN`）。tsw 生成任务书时据此写一行“语言：与用户交流……使用 <语言>”，不用你在目标里写。
- 用户说出以后都用的语言（例如“以后用英文和我交流”）时，按用户原话用 `config_change` 设置 `control.language`；之后生成或重新生成的任务书使用新值，已发出的任务书要等下次重新生成（`task_update`、续用、需求变更）。
- 只是某个任务要用别的语言（例如给外部同事的英文报告）时，不改配置，写进该任务的目标与验收。
- 它只决定与用户交流的语言；代码、commit message、PR 标题等按仓库自己的规则。

## 推荐读取集合（DN007 §7.2）

检索中入围、worker 需要参考的任务（做法、结论、用户决定的出处），在 `task_dispatch` 或 `attempt_continue` 的 `read_set` 中给出（本任务与依赖总在其中），并在目标的“背景”中写明各自的理由。它是 worker 读取的起点，不是限制。

## 写回与修改

- 用户实质修改需求：`task_update`（附用户来源）。用户在 worker 会话里直接给 worker 追加或修改要求时，不用你转录：只要任务还没被用户验收（不是 `accepted`、`cancelled`、`archived`），worker 会引用 hook 记录的用户原话自己登记（`requirement_change`，revision+1，DN002 §5.1a），在同一 attempt 内继续评审并重新提交。
- 之后的决定或其他任务的结论（例如另一个任务定下的设计、文档结构、接口约定）影响到已登记、尚未完成的任务时，立即用 `task_update` 写回该任务的目标与验收，附用户来源；用户还没有就这个任务表态时，先问用户，不要只记在本会话里等派发时再补。
- `task_update` 的结果带 `brief` 时，任务书已按新 revision 重新生成；其中有 `session_ref`（待命或执行中的会话）时，用消息告诉该会话：任务书已更新到 revision N（路径 `brief.path`），请重新读取。

## 按任务类型的附加说明

**code**

- 写明涉及的仓库规则：哪些改动按仓库规则需要用户确认才能合并、需要运行哪些 live 场景、合并后要核对什么。
- 需要用 gh 命令行建 PR、合并、查看 CI 等时，在目标中写明：“注意 gh 当前账号是否与仓库账号（<账号>）一致，不一致时按 `gh-account` skill（`<数据目录>/.claude/skills/gh-account/SKILL.md`）执行，不用 `gh auth switch`。”账号按该 skill 第 1 节确定（配置 `repositories.<仓库>.auth_profile` → `accounts.<名>.account`，或仓库 owner 对应的已登录账号）；确定不了时写“账号由 worker 按 skill 确定”。`<数据目录>` 写实际的绝对路径。
- 仓库在配置中没有 `auth_profile` 时，把建议的账号配置告诉用户；写入配置是权限类改动，按用户原话用 `config_change`。

**design**

- 写明产出的设计文档位置、需要用户确认的范围，以及设计批准不等于实现批准。

**research**

- 写明结论的形式（报告、表格、建议）、来源要求（引用出处、区分实测与推断），以及不改代码、不做不可逆的动作。
